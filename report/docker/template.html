Abstract

The Proximity Search API from Lab 7 (Flask + gunicorn, Dijkstra over a road-linkage file) was packaged as two containers: an api service built from a multi-stage python:3.12-slim Dockerfile, and a gateway service built from nginx:1.28-alpine that acts as the reverse proxy and serves the link files over HTTP. A single docker-compose.yml builds both images, creates a private bridge network and a named log volume, and starts the API first and the gateway only once the API passes its health check. docker compose up -d --build is the only command needed. All work was done on my personal laptop (Docker Desktop on WSL 2). The test suite passes inside a container (23/23), and 200 random queries sent through the stack returned exactly the same top-10 lists as the engine run natively. Twelve problems came up along the way; each one, with its cause and fix, is recorded in Section 4.

1Architecture of the stack

The Lab 7 application is one Python process. It loads the 10,000-location CSV at start-up, and for each /search/ request it parses the link file (or reuses a cached graph) and runs Dijkstra. I split the stack into two services: the application itself, and an nginx gateway in front of it. The gateway is the only container that can be reached from the host. It enforces the upload limit, forwards requests to gunicorn, and serves the links/ folder at /files/. That last job lets the API's "link as a URL" input work entirely inside the Docker network: link=http://gateway/files/link.txt is resolved by Docker's DNS to the gateway container.

2Docker design choices

2.1Base images

ServiceBase imageWhy
apipython:3.12-slim
(Debian, both stages)		Matches the Python 3.12 used in development. slim leaves out compilers and docs but keeps glibc, so wheels from PyPI install as-is (Alpine's musl would force source builds for some packages). Final image: 50 MB compressed content, 210 MB on disk.
gatewaynginx:1.28-alpineThe current stable nginx line, on Alpine because nothing here is compiled. The official image already runs envsubst over /etc/nginx/templates/*.template, so the upstream host and upload limit can come from environment variables without a custom entrypoint. Image: 26 MB compressed, 92.5 MB on disk.

Multi-stage build. The builder stage creates /opt/venv and installs Flask and gunicorn. The runtime stage starts again from a clean python:3.12-slim and copies in only the venv and the app (app.py, engine.py, gunicorn.conf.py, data/, links/), so pip's caches and build leftovers never reach the final image. requirements.txt is copied and installed before any source code, so editing engine.py reuses the cached dependency layer instead of reinstalling. A separate testdeps stage adds pytest to the same venv; the test target is runtime plus that venv plus tests/, so the shipped image never contains pytest.

Security. The API runs as appuser (uid 10001, no home directory, nologin shell). The application files are owned by root and read-only for that user, and both health checks use tools already in the base images (Python's urllib, BusyBox wget), so no curl package is added.

2.2Ports

ContainerPortExposure
gateway80/tcpPublished as ${HOST_PORT:-8080}:80, the only entry point from the host. 8080 avoids needing admin rights for port 80 on Windows; it can be changed in .env without editing YAML.

2.3Networks

One user-defined bridge network, proxnet. Compose would create a default network anyway, but naming it makes the topology explicit in the YAML and in docker network inspect. On a user-defined bridge Docker runs an embedded DNS server (127.0.0.11), so containers find each other by service name. nginx's upstream points at api:8000, and the API can download http://gateway/files/link.txt. I considered marking the network internal: true to cut the API off from the internet entirely, but that would break the API's documented feature of fetching a link file from any http(s) URL, so the network stays a normal bridge and isolation comes from not publishing the API's port.

2.6Start-up order, health and restarts

Each image defines a HEALTHCHECK: the API runs GET /health every 15 s and the gateway fetches /gateway-health. The gateway's depends_on uses condition: service_healthy, so nginx starts only after the API has loaded the dataset and is answering. The output of docker compose up shows api Waiting → Healthy and only then gateway Starting (Figure 4). Both services use restart: unless-stopped. CMD is in exec (JSON) form so that gunicorn is PID 1 and receives SIGTERM directly: docker compose stop api finishes in 0.9 s instead of waiting for the 10 s kill timeout (Error 3).

3.1Install Docker and check the installation

Docker on Windows runs Linux containers inside a lightweight VM managed by WSL 2, so the installation has two parts. These are the steps followed on this laptop:

  1. Check virtualisation. Hardware virtualisation (Intel VT-x on this laptop's Core i5-13500HX) must be enabled in the BIOS. Task Manager → Performance → CPU shows Virtualization: Enabled.
  2. Install WSL 2. In an administrator PowerShell: wsl --install. This enables the Virtual Machine Platform and Windows Subsystem for Linux features, installs the WSL kernel and an Ubuntu distribution, and needs one reboot. wsl --version then confirms WSL 2.6 with Linux kernel 6.6.
  3. Install Docker Desktop. Download Docker Desktop Installer.exe from docs.docker.com/desktop/setup/install/windows-install/, run it, and keep Use WSL 2 instead of Hyper-V ticked. It installs to C:\Program Files\Docker\Docker and adds the docker CLI, BuildKit (buildx) and the Compose v2 plugin to the PATH.
  4. First start. Launch Docker Desktop and accept the subscription agreement (free for personal and education use). On first start it creates its own WSL distribution, docker-desktop, which runs the Docker Engine, and a CLI context desktop-linux that connects to it through a named pipe. If the CLI is used before the engine is running, it fails with the named-pipe error in Error 1.
  5. Verify. docker version must show both a client and a server, and docker run hello-world must print its greeting.

4Errors faced and how they were resolved

These are the problems that actually came up, in the order they appeared, each with the evidence captured at the time.

1Docker engine not running

Symptom

docker ps → failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine … The system cannot find the file specified.

Cause

On Windows the docker CLI is only a client. It talks to the engine inside Docker Desktop's WSL 2 VM through a named pipe, and that pipe exists only while Docker Desktop is running.

Fix

Started Docker Desktop and polled docker info until the engine answered (Figures 2c and 2e).

{{SHOT:01_daemon_down|}}

2pip install timed out during the build (ReadTimeoutError)

Symptom

The build failed after 93 s: ReadTimeoutError: HTTPSConnectionPool(host='files.pythonhosted.org', port=443): Read timed out. Even the successful step that installed Flask took 110 s.

Cause

The internet connection to PyPI's file CDN was very slow, and pip's default read timeout of 15 s was shorter than some of its stalls.

Fix

Set PIP_DEFAULT_TIMEOUT=120 and PIP_RETRIES=10 in the builder stage. Later builds log WARNING: Retrying … and then succeed instead of failing (Figure 4a).

{{SHOT:04_pip_timeout_excerpt|}}

3Build-check warning: JSONArgsRecommended

Symptom

BuildKit warned: JSON arguments recommended for CMD to prevent unintended behavior related to OS signals (visible at the bottom of the previous screenshot).

Cause

The first Dockerfile used a shell-form CMD exec gunicorn --bind "0.0.0.0:${PORT}" … so that environment variables would be expanded. Shell form runs under /bin/sh -c, which may not pass SIGTERM on to gunicorn, so docker stop would wait 10 s and then kill it.

Fix

Moved the settings into gunicorn.conf.py, which reads PORT/WORKERS/THREADS from the environment (gunicorn loads it automatically from the working directory), and changed to CMD ["gunicorn", "app:app"]. Stopping now takes 0.9 s (Figure 13b).

4useradd warning: uid above SYS_UID_MAX

Symptom

useradd warning: appuser's uid 10001 is greater than SYS_UID_MAX 999 (top of the screenshot for Error 2).

Cause

--system asks for an account in the system range (< 1000), but I had also given a fixed high uid. A high uid is deliberate, since it cannot collide with any account on the host.

Fix

Dropped --system and gave the account a /usr/sbin/nologin shell instead: useradd --uid 10001 --no-create-home --shell /usr/sbin/nologin appuser.

5pytest could not write its cache inside the container

Symptom

The tests passed, but with PytestCacheWarning: could not create cache path /app/.pytest_cache … [Errno 13] Permission denied.

Cause

The container runs as appuser and /app is owned by root. This is intended: the running app must not be able to modify its own code.

Fix

Kept the permissions and turned off pytest's cache plugin in the test image: CMD ["python", "-m", "pytest", "-q", "-p", "no:cacheprovider"].

{{SHOT:06_run_tests|}}

6Docker Hub layer download: EOF

Symptom

While pulling nginx:1.28-alpine: error: failed to copy: httpReadSeeker: failed open … production.cloudfront.docker.com … EOF.

Cause

The connection to Docker Hub's CDN dropped partway through a layer download, again caused by the unreliable network.

Fix

During the build none was needed: BuildKit logged retrying in 1s, and the pull and the build then succeeded (Figure 5). The same EOF later hit docker run --rm hello-world (below), and that command does not retry: it exited with code 125. I re-ran the download on its own with docker pull hello-world, which succeeded, and docker run hello-world then worked (Figure 2d). So BuildKit retries registry downloads, but plain docker run and RUN pip install inside a build do not (Error 2).

{{SHOT:47_hello_world_eof|}}

7The log volume held nothing useful, and reading it hung the terminal

Symptom

/var/log/nginx in the named volume held only two symlinks, and tail /var/log/nginx/access.log never returned.

Cause

The official nginx image links access.log → /dev/stdout and error.log → /dev/stderr so that logs go to docker logs. When the empty named volume was first mounted, Docker copied those symlinks into it, so no log was ever written to disk, and tail on /dev/stdout blocks forever.

Fix

Added a second access_log /var/log/nginx/gateway_access.log; next to access_log /dev/stdout;. Logs now go to both docker logs and the volume (Figures 13a and 13e).

{{SHOT:22_volume_hang|}}

8Git Bash rewrote container paths (MSYS path conversion)

Symptom

docker compose exec gateway ls -l /var/log/nginx → ls: C:/Program Files/Git/var/log/nginx: No such file or directory.

Cause

Git Bash (MSYS2) converts any argument that looks like a Unix path into a Windows path before running a Windows program such as docker.exe. It treated /var/log/nginx as relative to Git's install folder, even though the path was meant for inside the Linux container.

Fix

Set export MSYS_NO_PATHCONV=1 for commands that pass container paths (Figure 13a). The same commands work unchanged in PowerShell, which does no such conversion.

10Every code change made the test build download pytest again (and time out)

Symptom

After a one-line change to the runtime stage (the useradd fix), rebuilding the test image ran pip install pytest again and failed with the same ReadTimeoutError after 230 s.

Cause

Layer-cache ordering. The test stage was FROM runtime followed by RUN pip install pytest, so any change in runtime (including any change to the source code) invalidated the pytest layer and forced a fresh download.

Fix

Added a testdeps stage (FROM builder) that installs pytest into the venv. That stage depends only on requirements.txt; test now copies the finished venv from it. Both pip steps also use a BuildKit cache mount, RUN --mount=type=cache,target=/root/.cache/pip, so downloaded wheels are kept between builds without ending up in an image. To check it, I appended a comment to engine.py and rebuilt: the source layer was rebuilt, the pip layers stayed CACHED, and the whole test image rebuilt in 2.3 s (the edit was then reverted).

{{SHOT:43_cache_after_code_change|}}

11No matching distribution found for flask>=2.2

Symptom

On the next build, pip could not even read the package index: Could not find a version that satisfies the requirement flask>=2.2 (from versions: none), after 137 s.

Cause

"from versions: none" means pip got no index page at all. The message looks like a version problem, but the cause was the network. To confirm it, I fetched https://pypi.org/simple/flask/ from the host (HTTP 200 in 0.4 s) and from a throwaway docker run --rm python:3.12-slim container (39 kB in 1.5 s). Both worked, so DNS and the index were reachable from containers, and the failure was intermittent.

Fix

Re-ran the build unchanged. It got past the index this time (Flask installed after one retry), but the next download stalled again. That led to the real cause, Error 12.

{{SHOT:37_no_match_excerpt|}}

12Downloads inside Docker were about 100× slower than on the host

Symptom

Even with retries, pip install pytest failed once more after 509 s with ReadTimeoutError. Small requests (index pages) worked, but files of a few hundred kB stalled.

Diagnosis

I downloaded the same 386 kB pytest wheel in different places. From the Windows host it took 0.5 s. From a container on the default bridge it either timed out or took 44 s. I suspected a path-MTU problem (common with WSL 2 and VPNs), so I created a bridge network with MTU 1400: still 55–65 s, so MTU was not the cause. With --network host (the VM's own network stack) it also failed. The bottleneck is therefore Docker Desktop's VM network path on this laptop, not the internet, the image or the Dockerfile. The successful build logged 16.9 kB/s.

Fix

The build was made tolerant of the slow link instead of depending on it: the pip timeout and retries from Error 2, and the cache mount from Error 10. The mount meant that the failed attempt's downloads were reused (Using cached pytest-9.1.1…), and the next build succeeded (Figure 4a). After that, every rebuild hits the layer cache and needs no network at all. The proper fix would be in Docker Desktop's network settings (or a restart of its VM). I left that alone because other containers on this machine depend on the same engine.

6What I learnt

  • Layer order decides how fast a rebuild is. Copying requirements.txt and installing it before copying the source means that a code change rebuilds in seconds. Error 10 showed the reverse: one stage built on top of another inherits every cache invalidation of its parent. Stages should depend on as little as possible.
  • Multi-stage builds separate build tools from what ships. The runtime image has the venv and the app but not pip's cache, and the test tooling lives in a target that is never deployed. One Dockerfile produces both images.
  • Exec-form CMD matters for shutdown. With shell form, /bin/sh is PID 1 and signals may not reach the app. Moving configuration into a file read from the environment kept the command static and made a stop take 0.9 s instead of 10 s.
  • depends_on alone only orders container start-up. A health check plus condition: service_healthy is what makes the gateway wait until the API can answer requests.
  • User-defined networks give service discovery for free. Containers reach each other by service name through Docker's DNS. Leaving a port unpublished keeps a service internal without any firewall rules.
  • An empty named volume is filled from the image the first time it is mounted. That is why the nginx volume held only the image's symlinks (Error 7). A volume is only useful if the process actually writes regular files into it.
  • Read error messages for what actually failed. "No matching distribution" was a network outage, not a version conflict. Testing the same request from the host and from a throwaway container isolated the cause in two commands.
  • On Windows, Docker runs Linux containers inside a WSL 2 VM. The CLI talks to it through a named pipe (Error 1), and the shell can rewrite arguments before Docker sees them (Error 8).
  • Containers make the result reproducible. The same test suite, and 200 random queries, gave identical answers in the container and natively. Anyone with Docker can now run the whole service with one command, without installing Python or nginx.
